问题：运行 scheduler_test 时 "balloc: out of blocks" 错误
================================================================================

【现象】
运行 scheduler_test 时内核 panic："balloc: out of blocks"

【原因分析】
xv6 文件系统默认只有 1000 个块（约 500KB），对于测试程序创建多个进程和
写入输出文件来说太小了。

【解决方案】
修改 param.h 中的 FSSIZE：
  #define FSSIZE 10000  // 从 1000 增加到 10000


================================================================================
问题4：PRIORITY/SML 调度器在交互响应测试中表现不佳
================================================================================

【现象】
场景2测试结果显示，PRIORITY 调度器下：
- CPU 背景任务（优先级18）平均就绪时间：13
- 交互型任务（优先级3）平均就绪时间：44

高优先级的交互型任务反而等待时间更长。

【原因分析】

1. 非抢占式调度
   PRIORITY 和 SML 调度器是非抢占式的，只在进程主动让出 CPU 时才重新调度。
   CPU 密集型任务没有 yield/sleep/exit 调用，会一直运行到完成。

2. setpriority 时机问题
   测试程序中，子进程在 fork() 后才执行 setpriority()：
     pid = fork();
     if(pid == 0) {
       setpriority(getpid(), 3);  // 子进程设置自己的优先级
       ...
     }
   
   问题是：在子进程设置高优先级之前，其他 CPU 密集型进程可能已经开始运行。

3. 进程创建顺序
   测试按此顺序创建进程：
   - 先创建 CPU 背景任务（fork 后立即开始运行）
   - 再创建交互型任务（此时 CPU 背景任务已在运行）
   
   CPU 密集型任务先获得 CPU 且不会让出，交互型任务必须等待。

【时间线图示】

    t=0  创建 CPU背景1 → 立即运行（优先级默认=10）
         [CPU背景1 运行中...]
    
    t=1  创建 CPU背景2 → 加入就绪队列
         [CPU背景1 继续运行...]
    
    t=2  创建 交互型1 → 加入就绪队列
         子进程执行 setpriority(12, 3)
         但 CPU背景1 仍在运行，不会被抢占！
         [CPU背景1 继续运行...]
    
    ...  CPU 密集型任务运行 22 个时钟周期
    
    t=22 CPU背景1 结束
         调度器选择下一个进程
         这时交互型任务才有机会运行

【解决方案】

方案A：实现抢占式优先级调度
  修改 trap.c，在时钟中断时检查是否有更高优先级进程就绪，
  如果有则强制当前进程让出 CPU。
  优点：最彻底的解决方案
  缺点：需要修改内核代码，增加调度开销

方案B：父进程设置子进程优先级
  在测试程序中，fork() 后由父进程立即调用 setpriority(pid, priority)
  在子进程加入就绪队列之前就设置好优先级。
  优点：修改简单
  缺点：只是测试层面的修复

方案C：调整进程创建顺序
  先创建高优先级任务，再创建低优先级任务。
  优点：简单
  缺点：不是通用解决方案


================================================================================
问题5：优先级在进程入队后修改不生效（堆/队列问题）
================================================================================

【现象】
优先级调度器使用最小堆，进程以默认优先级10插入堆后，
即使后续调用 setpriority() 修改优先级，调度顺序也不会改变。

【原因分析】
原实现使用最小堆存储就绪进程：
  struct proc *priorityScheduler() {
    return heapExtract();  // 从堆中取出
  }

进程插入堆时按当时的优先级确定位置。setpriority() 只修改 p->priority 字段，
不会重新调整堆结构。

【解决方案】
改为遍历进程表，实时检查当前优先级：
  struct proc *priorityScheduler() {
    struct proc *p, *best = 0;
    for(p = ptable.proc; p < &ptable.proc[NPROC]; p++) {
      if(p->state == RUNNABLE) {
        if(best == 0 || p->priority < best->priority)
          best = p;
      }
    }
    return best;
  }

时间复杂度从 O(log n) 变为 O(n)，但保证使用进程的当前优先级。

SML 调度器也做了类似修改，动态根据当前优先级分配队列级别。
